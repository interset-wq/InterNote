# AGENTS.md

## Project

InterNote — static blog generator (Python 3.14, uv, typer + pydantic + jinja2) that renders GitHub Issues into a GitHub-Pages site.
This repo is the **generator only**; posts, config, and CI live in a separate blog repo.
README is Chinese — keep new user-facing docs consistent.

## Commands

- `uv sync` — install deps (Python pinned in `.python-version`, requires `>=3.14`)
- `uv run pytest -q` — what CI (`.github/workflows/test.yml`) runs on every push/PR. It is green: `tests/test_frontmatter.py` (parsing), `tests/test_config.py` (schema), `tests/test_generator.py` (entry routing, front matter, post withdrawal, render cache), `tests/test_feed.py`. All offline — `FixtureRepo` in `fixtures.py` mirrors the PyGithub surface the generator uses, so prefer it over mocking. Two gaps to be aware of: `cli.py` and `renderer.py` are untested, and `FixtureIssue` must keep every attribute `generator.py` touches (`state` is easy to forget and breaks `run_one`).
- `uv run internote <token> <owner/repo> [--issue-number N]` — build a site. Needs a GitHub token and `config.toml` in cwd; writes `dist/`, `sources/`, `internote.json` and rewrites README stats. Do not run casually. `--issue-number` is the incremental path and only touches that one issue.
- Rendering is cached: `internote.json` carries a `render_cache` mapping sha256(stripped body) → HTML, pruned to the entries used each run. Editing an issue still costs exactly one `/markdown` call; an unchanged scheduled build costs none. The cache is loaded in `Generator.__init__`, not `_load_state`, because `run_all` does not load entry state.
- `uv run python scripts/fetch_fixtures.py <owner/repo> -o tests/fixtures/<owner>__<name>.json` — capture issues + pre-rendered markdown via `gh api` into a fixture JSON (uses your gh login, no token args).
- `uv run internote - <owner/repo> --fixtures tests/fixtures/<owner>__<name>.json` — offline build from a fixture (`src/internote/fixtures.py` provides a duck-typed repo + markdown). Use this for local previews and unit tests instead of pushing to verify; the committed fixture in `tests/fixtures/` is the shared test data.
- `uv build` — wheel; `src/internote/templates/` and `src/internote/plugins/` ship automatically (hatchling `packages = ["src/internote"]`), no pyproject change needed when adding files there.

## Layout & architecture

- `src/internote/` package: `cli.py` (entrypoint) → `generator.py` (orchestrator: build state `internote.json`, incremental `run_one()` vs full `run_all()`, README stats update) with `config.py`, `renderer.py`, `github_client.py`, `feed.py`, `frontmatter.py`, `constants.py` (i18n + icon SVG paths).
- Templates (`*.j2.html`) and plugins (`*.js`) live **inside the package** and are resolved via `Path(__file__)`, cwd-independent — do not move them to the repo root.
- Plugins are exactly six, all zero-dependency, all IIFE + `'use strict'`, **none inject CSS** (`theme.js` 3-state light/dark/auto, `toc.js` self-implemented TOC with scroll-spy, `fab.js` bottom-right floating buttons — TOC overlay + scroll up/down, post pages only below 1250px, reusing the `#in-toc` panel, `lightbox.js` image viewer, `code-copy.js` clipboard buttons, `giscus.js`). They are copied to `dist/plugins/` verbatim, **not** Jinja-rendered, so they get config from `data-*` attributes on server-rendered markup (`#in-toc[data-toc-title]`, `#in-fab[data-toc-title][data-top-title][data-bottom-title]`), never `{{ }}` placeholders. A seventh, `search.js`, is emitted unconditionally by `base.j2.html` and fetches the local `dist/search-index.json`.
- **`search` is local, not hosted.** The generator writes `dist/search-index.json` (`_write_search_index()`) — the site's single client-side data file, consumed by the search dialog (`plugins/search.js`), the homepage list (`post-list.j2.html`) and the tag page (`tag.j2.html`). Shape: `{label_colors: {name: "#hex"}, posts: [{title, labels, date, date_color, top, url}]}`. Records are pre-sorted by the generator (`top` desc, then date desc), so every client renders the same order for free. `plugins/search.js` fetches it once, then case-insensitively substring-matches title/labels; a `YYYY`-style date fragment in the query filters by date instead. There is deliberately no `[search]` config section — search is always on. The old `post-list.json` is gone; don't reintroduce a second listings file.
- **`window.icons` is narrowed to runtime-only icons**: the template renders every static glyph server-side via the `icon()` macro, so `window.icons` only carries what JS must swap at runtime (theme sun/moon/sync, code-copy copy/check) or apply to DOM built from `post-list.json` (tag page rows). Keep `generator.py`'s per-page crop in sync when adding icons.
- `templates/` is 4 page templates plus `components/`: `macros.j2.html` holds **all** shared UI (`icon`, `nav_link`, `theme_button`, `site_nav`, `branding`, `head_meta`) and is imported with `{% from ... with context %}` so macros can read `icons`/`i18n`; `footer.j2.html` and `comments.j2.html` are plain includes. `site_nav` uses `{% call %}`/`caller()` so a page supplies only its own buttons and gets the `<nav>` wrapper plus theme toggle for free. Icons render `d` server-side — do **not** reintroduce `setAttribute('d', ...)` hydration JS.
- `renderer.py` runs Jinja with `trim_blocks`/`lstrip_blocks` and **autoescape off** (post bodies are pre-rendered HTML from the GitHub API). `base.j2.html` owns the `<style>` wrapper: children fill `{% block style %}` with raw CSS text and base emits the tag only when non-empty.
- **Never mix the `hidden` attribute with inline `style.display`** — Chrome's UA `[hidden]` rule wins over an inline `display`, so the two must not be used on the same element. Toggle the `hidden` *property* in JS.
- `assets/` (main.css, primer.css — Primer 21 bundled, **no external CDN**) is copied to `dist/assets/` at build time; pages link it at `{{ home_url }}/assets/...`.
- **`main.css` is the only global stylesheet** — it also carries the TOC and lightbox sections. Templates emit no inline `<style>` except the user injection points (`post.style`, `site.index_style`, `layout.all_head`).
- **CSS naming**: every class the project owns uses the `in-` prefix so it cannot collide with Primer (which is bundled, not scoped). Prefixes: `in-site-` site chrome, `in-post-` a post, `in-nav-` navigation, `in-badge` badges, `in-comments-` comments, `in-post-list-` listings, `in-pagination`, `in-search-` / `in-tag-cloud` / `in-empty-state` the tag page, `in-footer-` footer, `in-toc-` table of contents, `in-lightbox-` image viewer, `in-code-block` / `in-copy-feedback` code blocks, bare `in-` for utilities. Colours and spacing come from the `--in-*` design tokens in `:root`, which alias Primer variables with a literal fallback (`var(--color-fg-default, #1f2328)`) so the site still renders if Primer changes. Breakpoints: 600px (mobile), 768px (lightbox controls), 1249px (TOC drops out of the gutter).
- Post bodies render inside Primer's `markdown-body` (GitHub-issues look); theme switching is 3-state light/dark/auto with no config keys, driven by `plugins/theme.js` off `internote_theme` in localStorage. Markdown-alert colors are injected by `generator.py` (`ALERT_BASE_STYLE`/`ALERT_STYLES`); task-list styles live in `main.css` (missing from the Primer bundle).
- Optional per-post TOML front matter lives in `frontmatter.py` and is split off in `_add_entry` **before** the body reaches the markdown renderer (otherwise GitHub renders the `+++` delimiters as an `<hr>`; GitHub stores issue bodies with CRLF endings and `split()` accepts them — `+++\r\n` and stray `\r` inside the block are stripped). Fields: `date`/`draft`/`comments`/`pinned`/`slug` — `title`/`description`/`head`/`style`/`script` were removed (the title is always the issue title, the description is always derived from the body, page injections come from `[layout]` config only) and listing them is now an unknown-key error; `labels` is rejected because GitHub issue labels drive the tag pages, and an issue with **no** label is published with the `default` label instead of being dropped (forcing labels was unreasonable — authors forget them). Anything unknown raises and fails the build. `comments = false` skips the giscus section on that page (post template checks `post.comments`); `pinned` (boolean) overrides the GitHub pin timeline events and drives the `top` sort key, so a post can be pinned without maintainer access to the issue page; `slug` (string) mints a root-level **alias** page that redirects to the canonical `post/<id>.html` (meta refresh + `location.replace` + noindex + canonical) — the canonical URL is always the issue-number address, renames never break it. Reserved slugs (`index`/`post`/`tag`/`rss`/`page\d+`/…, see `RESERVED_SLUGS`) are rejected; `slug = "about"` is allowed and earns a nav link on the index (ctx key `site.about`) and is excluded from the `search-index.json` listings — the nav button is the only entry point, so the index/tag page/search never duplicate it (canonical page, alias and feed are unaffected). Fixtures keep the **raw** body so the metadata survives, render `body_html` from the **stripped** body, and `fixtures.py` keys its lookup on the stripped form — `split()` is idempotent, which is what makes that work. Tests in `tests/test_frontmatter.py`.
- `scripts/fetch_fixtures.py` calls `gh` with an explicit `encoding="utf-8"`; without it the GBK locale codec crashes on non-ASCII issue bodies on Chinese Windows.
- `config.py` uses `ConfigDict(extra="forbid")` everywhere: any unknown key in `config.toml` is a hard error. Current schema = `config.sample.toml` (`[site]`/`[layout]`/`[comments]`/`[giscus]` plus optional `[[social]]` entries; no theme/nav/feed/version/search/features). `[site].favicon`: empty (default) = the generator downloads the blog repo owner's GitHub avatar to `dist/assets/favicon.png` and injects `<link rel="icon">`; a URL = download that image instead; `"none"` = no favicon. The download is cached via the avatar URL in `internote.json` and silently skipped (with a warning) on failure or in fixture mode — a flaky network must not fail the build. `[[social]]` = footer icons: `id` is a Simple Icons slug fetched from `cdn.simpleicons.org` into `dist/assets/social/<id>.svg` and inlined server-side by `_fetch_social_icons` (same `favicon_src` cache; a failed download warns and drops only that icon); `action` is `link`/`copy`/`qrcode` and the matching `url`/`username`/`qrcode` field is enforced by a `SocialLink` model validator. RSS/GitHub stay built-in footer buttons; the copy-toast and QR-overlay JS lives inline in `footer.j2.html`, driven entirely by `data-*` attributes on the server-rendered buttons.
- Template ctx: one flat `site` dict from `config.context()` (generator adds `blog_repo_url`, `label_color_dict`, and `about` — `{url, title}` of the conventional alias or null), plus `post` (post page data), `icons` (cropped per page), `i18n`. `post-list` is the list template name (`plist` is gone).
- URLs: posts are always `post/<issue#>.html`; front matter `slug` only adds a root alias redirect. The index (`index.html`) and `tag.html` are client-rendered shells fed by `dist/search-index.json` — pagination is client-side via `#p=N` hash, no `pageN.html` files are generated.

## Two-repo flow (get this wrong and you break the live blog)

- Blog repo = Issues (labels optional; unlabelled issues publish as `default`) + `config.toml` + `.github/workflows/internote.yml` (copy of `examples/blog-workflow.yml`). This repo never stores posts.
- Blog CI **clones this repo** into `/opt/Internote` (always HEAD of `main`; the old `site.version` pinning was removed), overlays the blog files, runs the CLI, commits artifacts back, deploys Pages.
- **Schema sync**: a `config.py` change must be applied to the blog repo's `config.toml` and, if the workflow changed, to `.github/workflows/internote.yml` in the same change — `extra="forbid"` turns stale blog keys into a hard build failure. (GitHub contents-API `PUT` on that repo's workflow paths 404s; clone the blog repo and push instead.) Normalise the workflow file to the blog repo's line endings (it is LF) or the whole file shows as changed.
- Therefore: **pushing to `main` here changes the live blog** at the next build (any issue edit, or manual dispatch — there is deliberately no cron).
- `dist/`, `sources/`, `internote.json` are git-ignored here but must be committed by the blog repo (README `.gitignore` warning).
- Local deploy trigger: `gh workflow run internote.yml -R interset-wq/interset-wq.github.io` then `gh run watch <id> -R interset-wq/interset-wq.github.io --exit-status`.

## Conventions

- No TDD/SDD: do not write failing tests first or follow spec-driven development (too slow / token-heavy). Keep existing tests passing (`uv run pytest -q` before committing); add/adjust tests only when touching tested behavior. Commits atomic with English semantic prefixes (`feat:`/`fix:`/`refactor:`/`docs:`/`chore:`).
- Only `main` branch; push only with explicit user approval (global rule).
- `temp/` is git-ignored scratch space for this project (scripts, config copies).
